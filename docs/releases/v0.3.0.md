## Summary
- DockGuard now manages GUI apps such as Xcode and PostgreSQL clusters, alongside Docker Desktop.
- Every managed app is checked before it starts and counted by the eject rule, so `stop --eject` won't unmount the drive under a running database or app.

## Highlights
- New `app` kind: `symlink_paths` (such as Xcode's `DerivedData`) must each resolve to the drive. `start` opens the app; `stop` asks it to quit, only once it's confirmed running.
- New `postgres` kind for clusters run with `pg_ctl`. It checks the version against a required `bin_dir`, a stale `postmaster.pid` and the port. `start` passes only the configured options; `stop` uses fast mode. Any PostgreSQL version, or several side by side, is just another entry.
- `~/Library/Developer/CoreSimulator/Devices` is rejected as a linked path, including through symlinked folders: simulators break on an external drive.

## Behaviour changes
- Paths in the current config format must be absolute or start with `~/`. v0.1 config files are read as before.
- A `postgres` target always writes its server log to a file: `log_file`, or `<data_dir>.log` when it isn't set.

## Upgrading
- To manage more than Docker Desktop, move a v0.1 config to the current format (`examples/dockguard.yaml`). The v0.1 format still works, for Docker only.
- For each PostgreSQL cluster, set `bin_dir` to the cluster's own version, for example `/opt/homebrew/opt/postgresql@17/bin`. DockGuard never uses the `pg_ctl` on the PATH, because Homebrew's `libpq` can put a different major version there.

## Notes
- Apple `container` stacks (for example Fizzy) arrive in v0.4.0. Until then, stop them by hand before `stop --eject`.
