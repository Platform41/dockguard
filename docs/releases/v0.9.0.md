## Summary

DockGuard can now clear what blocks the drive instead of only naming it. When processes or
containers outside your configured targets are in the way, it offers to stop them one at a time,
and it never touches what it must not: other users' processes, its own terminal, protected macOS
processes and container or VM runtimes (D-025, amending D-019 and D-024).

## Added

- **`dockguard holders`** lists every process holding the mounted drive with its class:
  `stoppable`, `other user`, `self`, `protected` or `managed runtime`, and a hint for those it won't
  stop. Exit 0 when the drive is clear, 1 when processes hold it, 2 when inspection fails.
- **`dockguard holders --stop`** asks about each stoppable process: `Quit it? [Y/n]` sends a normal
  quit request; if the process still holds the drive after up to five seconds,
  `Force-quit it? Unsaved work will be lost. [y/N]` sends `SIGKILL`. DockGuard re-verifies the
  process (ID, start time, name, owner, executable and drive use) before each signal, so it never
  signals a recycled process ID. Finder is stoppable; macOS relaunches it.
- **Eject flows ask too.** In a terminal, `stop … --eject` offers the same questions after targets
  stop, then ejects once the drive is clear. Without a terminal DockGuard asks nothing and prints a
  `kill <pid>` command for each stoppable process.
- **Unmanaged containers.** When containers outside every configured stack block stopping a
  `container-system` target, DockGuard asks `Container <name> is running and isn't managed by
  DockGuard. Stop it? [Y/n]`, runs `container stop` (never delete), and prints the
  `container start <name>` command to bring it back. The deprecated `stop_system` pass keeps its
  previous refusal.
- **Dashboard:** `E` (stop all and eject) asks the same questions in order; a new `p` key, shown
  when processes hold the drive, offers them without ejecting. `y`/`n` answer, Enter takes the
  shown default, `esc` cancels the remaining questions.

## Never stopped

Root-owned and other users' processes (DockGuard uses no sudo), DockGuard itself and the terminal
it runs in, protected macOS processes (matched by executable path), and container and VM runtimes:
Apple container's own binaries, macOS Virtualization and Docker Desktop. Stop those through their
DockGuard target or `container stop`.

## Deprecated

- **`stop_system`** (D-017) still works without a `container-system` target. Its removal is
  postponed to v0.10.0.

## Validation

- Full Go suite (600 tests including subtests), race-enabled suite, `CGO_ENABLED=0` suite,
  `go vet` and `gofmt` pass on merged `master` (`d53971b`), run from a normal terminal.
- Maintainer live check on the external drive with a build of merged `master` from the main
  checkout, all passed: dashboard `p` polite quit, force-quit declined then accepted, `esc`
  cancelling the remaining questions, container runtime and VM processes never offered while a
  container stack ran; `stop container` blocked by a throwaway unmanaged container, stopped on yes
  with the restart hint; `stop --all --eject` in dependency order with the drive ejected.

## Compatibility

No config changes. With nothing holding the drive and no unmanaged containers, behaviour and output
are the same as v0.8.0. The process inspection uses macOS system calls only; no cgo or new
dependency.
