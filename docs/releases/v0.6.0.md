## Summary

Container targets can now prove they are usable before `start` reports success, and can say that
stopping them discards their data. A recipe shows both with AWS Emulator running on Apple
`container`, with no Docker involved (D-020).

## Added

- `ready` and `ready_timeout_seconds` on the `container` kind. After `up` succeeds, `start` runs the
  `ready` script once per second until it exits 0 (`<target> started and ready (N s).`) or the
  deadline passes (`<target> started but not ready after N s.`, exit 1, container left running).
  Each attempt is capped at five seconds or the time left, and a hung script and its child
  processes are killed at the deadline. Readiness runs only during `start`.
- `ephemeral` on the `container` kind. `list` and the dashboard show `(ephemeral)` after the
  state, and `<target> is ephemeral: its data is discarded on stop.` prints immediately before the
  target's `down` script runs.
- Recipe `docs/recipes/aws-emulator.md`: AWS Emulator 1.0.385 as a `ready` + `ephemeral` target,
  pinned by versioned URL and by the SHA-256 of the signature-verified package, with the full SDK
  environment so clients cannot fall through to real AWS.

## Validation

- Full Go suite (224 tests) and race-enabled suite pass on merged `master`; `go vet` passes.
- Live checks on the T7 with the real `aws-emulator` target: preflight includes the `ready`
  check; `start` reports ready in about a second; `list` shows `running (ephemeral)`; S3 works with
  the documented SDK environment; `stop` prints the discard notice, a second `stop` prints
  `is already stopped.` with no notice; `stop --all --eject` stopped every target and ejected the
  drive.
- A `ready` script that never exits returned not-ready at its 3-second deadline with no orphaned
  child process.

## Compatibility

New optional keys only. Configs without `ready` or `ephemeral` behave exactly as in v0.5.1,
including `start`, `stop` and `stop --all` output, stop order, eject readiness and dashboard
confirmations.
