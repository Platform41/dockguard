## Summary

DockGuard now knows what each target needs. Targets declare `depends_on`, the Apple container
system becomes a target of its own, and one command acts on one target: DockGuard asks before it
also starts a missing prerequisite or stops the targets that depend on one (D-024, amending D-017).

## Added

- **`depends_on`** on every target kind. Unknown names, self references, duplicates and cycles are
  config errors; a cycle is shown in order (`a → b → a`).
- **`container-system` kind** for Apple's shared container service: `start` runs
  `container system start` and confirms it running; `stop` runs `container system stop` and refuses,
  naming them, while containers outside every configured stack are running. A running or unknown
  system blocks eject.
- **Start and stop prompts.** `dockguard start <target>` with a stopped prerequisite asks
  `Start container first? [y/N]`; on yes it runs each prerequisite's preflight and start, deepest
  first, confirmed running before the next. `dockguard stop <target>` with running dependents asks
  `Stop them first? [y/N]`; on yes they stop in reverse dependency order, each confirmed. The default
  is No. Without a terminal, DockGuard asks nothing and prints the exact commands to run instead.
  A prerequisite in an unknown state is refused, never offered.
- **Dependency-ordered `stop --all [--eject]`.** Dependents stop before what they need; independent
  targets keep reverse config order. A target that fails to stop keeps its prerequisites running and
  reports them; any failure prevents eject.
- **Dashboard:** each row shows its dependencies (`container  → container`); `s` and `x` ask the same
  questions. The plan is recomputed when you answer, so a change in the meantime cancels instead of
  acting on a stale answer.

## Deprecated

- **`stop_system`** (D-017). Configs without a `container-system` target keep the v0.7.0 behaviour,
  including the shared-system pass after `stop --all`, and `list`/`status` print a deprecation line
  for each target using it. A config with both a `container-system` target and `stop_system: true`
  is rejected. `stop_system` is removed in the next release; see "Migrating from `stop_system`" in
  the README.

## Validation

- Full Go suite (492 tests) and race-enabled suite pass on merged `master` (`491961b`); `go vet` and
  `gofmt` clean.
- Built-binary checks: the `stop_system` conflict and a dependency cycle are reported as config
  errors naming the target.
- Maintainer live check on the T7 with a build of merged `master` from the main checkout, after
  migrating a real config (a `container-system` target, `depends_on` on three container stacks,
  `stop_system` removed, `container system start` removed from their up scripts), all passed: start
  refused on No and without a terminal; start with `y` bringing up the container system, then the
  stack, with its data intact; stop of the system refused on No (singular message); dashboard
  dependency column and `x` confirmation; stop with `y` stopping the stack before the system;
  `stop --all --eject` in dependency order with the drive ejected.

## Compatibility

New optional key (`depends_on`) and kind (`container-system`) only. Configs without them behave as
in v0.7.0, apart from the `stop_system` deprecation line. Migrating changes your config and scripts;
updating the binary alone doesn't migrate them.
